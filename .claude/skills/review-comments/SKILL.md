リポジトリのすべてのコメントを、[`CONTRIBUTING.md`](../../../CONTRIBUTING.md) の「コメント」の規約で精査する。
おもな目的は、変わらないまま古くなったコメントを見つけること。こうしたコメントは、差分の確認では見つからない。

起動後は、手順 3 の報告まで確認を挟まずに進めてよい。ファイルは、手順 4 でユーザーが選んだ範囲だけを直す。

## 1. 対象を集める

1. `git ls-files` で、コメントを書けるファイルの一覧を作る
2. ロックファイルと、ツールが書き出すファイル（`pnpm-lock.yaml` など）を対象から外す
3. 一覧を、トップレベルのディレクトリを単位に分ける。ファイルの多いディレクトリは 1 つ下の階層で分け、少ないものはまとめて、量をそろえる

## 2. 精査を任せる

分けたまとまりごとに [`comment-reviewer`](../../agents/comment-reviewer.md) サブエージェントを並列で動かし、ファイルの一覧を渡す。
すべてのファイルのコメントとコードを 1 つの会話で読むと、報告をまとめる前にコンテキストが埋まるため。

報告に根拠のない結果があれば、そのまとまりのサブエージェントに続けて確認させる。

## 3. 量を測って報告する

1. リポジトリのルートで次のコマンドを実行し、コメント行の割合・4 行以上続くコメントのかたまりの数・いちばん長いかたまりの行数を測る。
   前回の精査の PR に、このコマンドで測った数があれば比べる。報告には、このコマンドで測ったことも書く

   ```bash
   .claude/skills/review-comments/count-comments.sh
   ```

2. サブエージェントの報告をまとめる。同じ問題が複数のまとまりから出ていたら 1 つにし、サブエージェントの分類ごとに `path:行番号`・問題・直し方の案・根拠をそろえて報告する
3. 確認していないことは「未確認」、根拠から組み立てた見立ては「推測」と書く。外部の仕様についての主張を、どこまで確認したかも伝える

## 4. 直す範囲を選ばせて直す

1. 分類ごとに直すかを `AskUserQuestion` で選ばせる。設定の値を変えるなど、動作が変わる直し方は別の問いにして候補を示す
2. `main` にいるなら、[`CONTRIBUTING.md`](../../../CONTRIBUTING.md) の規約で作業ブランチを切ってから直す
3. 選ばれた範囲だけを直し、変えた箇所と確認した結果を伝える。コミットや PR の作成は、ユーザーに頼まれるまで始めない

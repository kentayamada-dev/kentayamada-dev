## ルールや手順を書くとき

<!--
例は Claude の出力の形式や構造をそろえる、もっとも確実な方法の 1 つとされている
https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#use-examples-effectively
-->

- 書き方や形式が文だけでは伝わりにくいルールには、例を添える
- 例は実際に動かして確認したものだけを載せる。確認できないものは載せないか、「未確認」と明記する
- 例が 1 つだと、その場面にしか当てはまらないと読まれやすいので、場面の違う例を並べるか、当てはまる範囲を文で補う

## 疎結合に書く

- ほかのツール・スキル・ファイルの名前や場所は、なくても伝わるなら書かない
- 例は、どのファイルのどこから取ったかを示さず、それだけで読める形にする

## リポジトリのファイルを指すとき

<!--
GitHub は、リポジトリのファイルのなかの相対リンクを、そのファイルからの相対パスとして解決する
https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#relative-links
-->

リポジトリで管理しているファイルとディレクトリを指すときは、リンクにする。
パスで書くときも、「portfolio の Dockerfile」のように名前で書くときも同じ。
リンクは CI で検査されるので、ファイルを移したり消したりすると、古い参照が見つかる。

- パスで書くときは、リンクの文字をパスのコードにする。リンク先は、その文書からの相対パスにする
- 同じファイルを何度指すときも、毎回リンクにする。リンクにしたパスを、2 回目から名前だけで書くなら、コードでよい
- 次のものはリンクにしない
  - コードブロックのなか
  - まだないファイルと、1 つに決まらないもの
  - PR・issue・コメントに貼るひな形のなか。貼った先には、相対リンクの基準になるファイルがないため
  - スキルなどのフロントマター。YAML の値は Markdown として扱われないため
  - CLAUDE.md などに書く `@` のインポート。Claude Code が決めた書き方のため

[`docs/`](../../docs/) の文書なら、次のように書く。

```markdown
CLI のツールは、[`.github/mise.toml`](../.github/mise.toml) に足す。足すときの手順は、`mise.toml` のコメントにある。
pnpm の版は [portfolio の Dockerfile](../.devcontainer/portfolio/Dockerfile) だけで管理する。
```

次のように分ける。

- リンクにする: ディレクトリのパス（ファイルと同じ）
- リンクにする:「次のスクリプト」のように、名前で 1 つのファイルを指すとき
- コードでよい: リンクにしたパスを、2 回目から `mise.toml` のように名前だけで書くとき
- リンクにしない: ツールごとのディレクトリにある `pnpm-workspace.yaml`（1 つに決まらない）
- リンクにしない:「ワークフローのコメント」のように、どのファイルとも決まらないとき
- リンクにしない:「main のルールセット」のように、GitHub の設定を指すとき（ファイルではない）
- リンクにしない: これから作るファイルのパス（まだない）
- リンクにしない: git が使う `.git/config`（リポジトリで管理していない）

## 表と図を使うとき

<!--
GitHub は Issues・PR・Discussions・wiki・Markdown ファイルで Mermaid を描画する
https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams
-->

文で書くと読み手が頭のなかで組み立て直すことになる内容だけを、表や図にする。

- 表にするのは、2 つ以上の項目を同じ観点で比べる・対応づけるとき
  - 観点が 1 つなら箇条書きにする
  - セルには短い語句だけを入れ、説明が要るなら表の下に書く
- Mermaid の図にするのは、つながりが文の順に並ばないとき（分岐・合流・ループ・間接の依存・複数の主体のやりとり）
  - 一直線の手順は番号つきの箇条書きにする
  - 図だけにせず、図の前に要点を 1〜2 文で書く
  - 1 つの図には 1 つのことだけを描く。ノードが増えるなら図を分ける
- Claude が読む文書（CLAUDE.md・スキル・ルール）には Mermaid を書かない。描画されず、ソースのまま読まれるため
  - 人が読む出力（PR やコメント）のひな形に入れる図は除く
- ファイルやコードを見ればわかる構造は、表や図にしない。変えると古くなるため

次のように分ける。

- 表にする: 内容ごとの書く場所（内容と書く場所を対応づける）
- 表にしない: ツールの名前の一覧（観点が 1 つなので箇条書き）
- 図にする: ワークフローがスクリプトを通して外部 API を呼び、結果を PR に書き戻す流れ（間接で、戻りがある）
- 図にしない: インストール → 設定 → 起動のような手順（一直線なので番号つきの箇条書き）
- 図にしない: ディレクトリの構成（見ればわかり、変えると古くなる）

## README の書き方

<!--
GitHub はルート → docs/ の順で README を表示するため、docs/README.md ならリポジトリのトップは自己紹介のまま
https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes
-->

ルートの [`README.md`](../../README.md) は GitHub のプロフィールに表示される自己紹介なので、開発の内容を書かない。
開発の文書の入口は [`docs/README.md`](../../docs/README.md) にし、概要と開発環境の始め方だけを書く。
テーマごとの詳しい内容は、[`docs/`](../../docs/) のほかの文書に書く。
この節の「README」は [`docs/README.md`](../../docs/README.md) を指し、[`docs/`](../../docs/) のほかの文書も含む。
[`docs/`](../../docs/) に文書を足したら、[`docs/README.md`](../../docs/README.md) のドキュメントの一覧にも足す。

内容ごとに、書く場所を次の表で決める。

| 内容 | 書く場所 |
| --- | --- |
| 使い方と挙動（何をするか・何を対象にするか・どう操作するか） | README |
| 1 か所の設定やコードに結びつく理由 | その設定やコードのコメント |
| その行を編集する人だけが要る手順 | その行のコメント |
| 複数の箇所にまたがる理由と、JSON などコメントを書けないファイルの理由 | README |
| 使う人と編集する人の両方が要る内容 | README とコメントの両方 |

理由をコメントに書いたときは、必要に応じて README で「理由は〜のコメントに書いている」と案内する。

- make のターゲットの一覧や、ターゲットとスクリプトが内部で実行するコマンドは書かず、そのファイルへのリンクにする。中身を変えると古くなるため
- アプリのエンドポイントや応答の中身は書かない。コードを読めばわかり、アプリを変えると古くなるため

次のように分ける。

- 書く:「`429`・`502`・`503`・`504` は成功として扱う」（挙動）
- 書かない:「レート制限の `429` は、リンク切れとは限らないため」（理由。コメントにある）
- 書かない:「`USER_NAME` を変えるときは、両方の `devcontainer.json` の `remoteUser` も合わせる」（編集する人向け。コメントにある）
- 書く:「版は [portfolio の Dockerfile](../../.devcontainer/portfolio/Dockerfile) だけで管理し、Renovate が更新する」（pnpm の版。使う人と編集する人の両方が要る）
- 書く: mise の設定を [`.github`](../../.github) に置く理由（複数のワークフローにまたがり、1 か所のコードに結びつかない）
- 書かない: ターゲットごとの動作やコマンドを並べた表（ファイルを見ればわかる）
- 書く:「ほかのスクリプトは、[`portfolio/package.json`](../../portfolio/package.json) にある」（ファイルへのリンク）
- 書かない:「`GET /hello` に `{"message":"hello from typescript"}` を返す」（アプリの応答の中身）

## 版の番号

- いま使っている依存の版の番号は、文書に書かない
- 版のタグで固定した根拠のリンクや、PR のタイトルの例のように、ある時点の版を示すものは書いてよい

次のように分ける。

- 書かない:「`node`（Node.js 26）」
- 書かない:「pnpm 12 は、1 つ目の文書に pnpm 本体の版を書く」（「pnpm は」とする）
- 書く: `blob/v2.102.0/` のように、版のタグで固定した根拠のリンク

## CI の検査に通る書き方

- `.md` はすべて CI で文章と書式を検査される
- 1 文を 100 文字以内にし、表記は [`.github/textlint/prh.yml`](../../.github/textlint/prh.yml) に合わせる
